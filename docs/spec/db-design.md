# Service: db-design (Design — 설계부)

> 버전 중심의 **설계 저작** 서비스. 활성 설계(Design)의 도면을 짓고 버전을 컷한다.
> **환경(Environment)·연결(Connection)과 무관** — 이 서비스의 어떤 화면도 실 DB 에 DDL·DML 을 실행하지 않는다.
> 위계: Service > Surface > Section > Component. ID 는 코드·테스트와 기계 대조용 안정 키.

## 이 문서의 범위 (정본 흡수 현황)

이 문서는 **steward spec 단계를 거친 Surface 부터** 점진적으로 채운다(`docs/spec/README.md` 흡수 원칙).

## 공통 불변식 (Design 전역)

- 키·표식은 **텍스트 배지만** 쓴다(`PK`·`FK`·`UK`·`IDX`·`CHECK`·`짝짓기`·`포함`·`무시`). 열쇠 이모지 등 애매한 기호 금지.
- 저장은 **설계 스코프 교체** — 설계 X 저장이 설계 Y 행을 건드리지 않는다(에이전트(MCP)·화면 동시 작업 안전).
- 활성 설계가 없으면 모든 Surface 는 설계 선택 안내를 보이고 빈 상태로 남는다.

## Surface: db-migration.seed (Migration › Seed — 시드 반영·되먹임 화면)
> 설계 시드를 실 DB 에 반영하고, 실 DB 행을 설계로 되먹인다. 계약은 `db-design.seed.apply-contract`.
> (nav 는 운영부 Migration 에 있지만 규칙의 정본은 이 문서다 — 시드의 뜻이 설계부에서 정의되므로.)

- **AC-1** 활성 연결·설계가 둘 다 있어야 하고, 시드 세트가 없으면 Design › Seed 로 안내한다.
- **AC-2** `설계 → 운영` 탭: `계획 만들기` → 요약(넣기·고치기·삭제 후보·변경 없음) + **막는 것 목록** + 실행할 문장 목록(파라미터 바인드 SQL, 참조 순서로 정렬). 막는 것이 있으면 `적용` 을 내주지 않는다.
- **AC-3** `적용` → 트랜잭션 게이트(영향 행수) → `커밋`/`롤백`. 커밋하면 이력에 `seed-apply` 로 남기고 계획을 다시 만든다(멱등 확인).
- **AC-4** `운영 → 설계` 탭: `실 DB 읽기` → 후보 목록(`설계에 없음`·`값이 다름`·`실 DB 에 없음`) → **고른 것만** `설계에 담기`. `실 DB 에 없음` 은 사실 보고이며 채택 대상이 아니다.
- **AC-5** 변수 값 입력은 이 화면에서 한다(환경 단위). 채워졌는지만 보이고 값은 다시 보이지 않는다.
- **AC-6** 조회 상한(`ROW_FETCH_CAP`)에 걸린 테이블은 계획이 불완전할 수 있다고 알린다.

## Surface: db-design.seed (Seed 뷰 — 기준 데이터 저작)

> **시드**(= 테이블을 만들 때 처음부터 있어야 하는 기준 데이터: roles·permissions·코드표)를 설계에 저작한다.
> Remote › Data 와 화면 형태(그리드)는 같지만 대상이 다르다 — Data 는 실 DB 에 지금 담긴 데이터,
> Seed 는 **설계가 정의하는 기준 데이터**다. 스키마 요소는 아니지만 서비스 정책·제약의 바탕이므로
> **버전 Diff 대상**이다.
>
> 관리 단위는 테이블 전체가 아니라 **시드 세트**(대상 테이블 · 짝짓기 기준 · 무시 컬럼 · `설계에 없는 행` 처리).
> 이 선언이 있으면 `{설계→운영}` 반영은 UPSERT 로, `{운영→설계}` 되먹임은 짝짓기 기준 행 단위
> 비교 + 선별 채택으로 성립한다. 두 방향 모두 **후속 범위**이며, 이 Surface 는 저작과 Diff 까지다.

### Section db-design.seed.set-list — 시드 세트 목록
- **AC-1** 활성 설계의 시드 세트를 테이블 이름순으로 보이고, 각 행 우측에 행 수를 표시한다.
- **AC-2** `+` 로 **설계 테이블 중에서** 세트를 만든다. 이미 세트가 있는 테이블과 뷰(`isView`)는 고를 수 없다(뷰는 데이터를 담지 않으므로). 고르기 목록의 검색·테이블/뷰 가르기는 공용 순수 로직(`db/tableList`)을 재사용한다.
- **AC-3** 세트 삭제는 확인을 받는다. 세트를 지워도 설계 테이블 정의는 건드리지 않는다.
- **AC-4** 세트가 하나도 없으면 빈 상태 + "테이블에서 시드 세트 만들기" CTA 를 보인다.
- **AC-5** 짝짓기 기준이 선언되지 않은 세트는 목록에서 `짝짓기` 경고 표식을 단다(AC 는 declaration AC-2 로 이어짐).
- **AC-6** 목록의 바깥 틀·행·구역 머리·빈 상태는 다른 DB 사이드 패널과 **같은 부품**을 쓴다(`shell/WorkspacePanels` + `db/sideList`) — 담는 것만 시드 세트일 뿐 생김새가 화면마다 달라지지 않게. 규칙 정본은 `db-design.definition.side-panel`.

### Section db-design.seed.declaration — 세트 선언 (짝짓기 기준·무시 컬럼·설계에 없는 행 처리)
- **AC-1** **짝짓기 기준**(= 어느 행이 이미 있는 행인지 알아보는 기준 컬럼)을 1개 이상 선언한다. 내부 필드 이름은 `naturalKey` 지만 화면 용어로 `자연키`를 쓰지 않는다 — 값을 고정해 심는 UUID 처럼 **자연키가 아닌 컬럼도 기준이 될 수 있어** 그 말이 실제 규칙보다 좁다. 기본값은 그 테이블의 PK 컬럼들이되, **PK 가 자동증가**(`AUTO_INCREMENT`·`serial`·`identity`)면 기본값을 비우고 사람이 고르게 한다 — 환경마다 값이 달라 짝짓기 기준이 될 수 없기 때문.
- **AC-2** 짝짓기 기준이 비면 행 저작은 되지만 **Diff 는 행 단위로 비교하지 않고 그 세트를 `비교 불가`로 표시**한다. 화면은 무엇이 없어 그런지 알린다.
- **AC-3** **무시 컬럼**(= 환경마다 달라도 차이로 보지 않을 컬럼: `id`·`created_at` 류)을 여러 개 고를 수 있다. 짝짓기 기준 컬럼은 무시 컬럼으로 고를 수 없다(상호 배타).
- **AC-4** 반영할 때 **설계에 없는 행**을 어떻게 할지 고른다: `그대로 둠`(기본 — 설계에 적힌 행만 넣고 맞추고 나머지는 건드리지 않는다) / `삭제 후보`(목록 전체를 설계가 결정하는 표). 라벨은 추상적 이름이 아니라 **효과 그대로** 쓴다 — 화면만 보고 무슨 뜻인지 알아야 한다. `삭제 후보` 를 고르면 그 뜻을 경고로 함께 보인다. **실제 삭제는 이 화면에서 일어나지 않는다** — 후속 반영 단계의 트랜잭션 게이트 몫.
- **AC-5** 선언 변경은 즉시(자동) 저장된다.
- **AC-6** 짝짓기 기준을 **UNIQUE 가 뒷받침하지 않으면** 그 사실을 안내한다(오류 아님 — 저작·비교는 그대로 된다). 판정은 짝짓기 기준과 **정확히 같은 컬럼 구성**의 PK/UK 가 설계에 있는지로 한다(순서 무시, 부분집합 불인정 — UPSERT 의 충돌 대상은 컬럼 구성을 그대로 지목하므로). 안내는 반영 단계의 함의를 말한다: UPSERT 를 못 써 "찾아서 넣기"로 내려가고 동시 실행 시 같은 행이 두 번 들어갈 수 있다.
- **AC-8** **DB 가 값을 만드는 컬럼은 짝짓기 기준으로 고를 수 없다** — 자동증가, 또는 기본값이 DB 함수(`uuid()`·`gen_random_uuid()`·`now()` 류). 환경마다 값이 달라 "같은 행"을 판단할 근거가 못 되기 때문. 역할 토글은 그 컬럼에서 `짝짓기` 를 건너뛰고(`포함 → 무시 → 포함`), 왜 못 고르는지 그 자리에서 알린다.
- **AC-9** 짝짓기 기준에 **환경 간 안정적인 컬럼이 1개 이상** 없으면 그 세트를 `반영 불가` 로 표시한다(저작·비교는 그대로 된다). 옛 설계·역설계로 들여온 세트가 DB 생성 컬럼을 기준으로 갖고 있을 수 있어 화면 제한과 **별도로 판정**한다.
- **AC-7** 시드 값은 **그대로** 실 DB 에 들어간다 — 어떤 자동 변환도 없다(값을 지어내지 않는다). 유일한 예외는 변수 자리표시자이며, 그것도 사람이 환경에 넣어 둔 값으로 치환될 뿐이다.

### Section db-design.seed.grid — 행 저작 그리드
- **AC-1** 그리드 컬럼은 그 테이블의 **설계 컬럼 순서**를 따른다. 컬럼 머리에서 그 컬럼의 **역할을 그 자리에서 지정**한다 — 역할은 `짝짓기`(기준) / `포함`(값을 맞출 대상, 기본) / `무시`(비교에서 뺌) 셋 중 **정확히 하나**이고, **버튼 하나**를 누를 때마다 `짝짓기 → 포함 → 무시 → 짝짓기` 로 돈다(세 상태가 한 축이라 토글도 하나다). 텍스트 배지만 — 이모지 금지. 편집 가능할 때는 이 토글 자체가 상태 표시를 겸하고, 읽기 전용(커밋 버전 열람)에서는 같은 뜻의 배지로 보인다(기본값인 `포함` 은 배지를 그리지 않는다). 무시 컬럼은 흐리게 그린다.
- **AC-1b** 긴 타입 라벨(예: `ENUM('a','b',…)`)은 **잘라 그리고** 전체는 툴팁으로 본다 — 타입 하나가 컬럼 폭을 독차지해 값이 안 보이는 것을 막는다(표시와 폭 계산이 같은 상한을 쓴다).
- **AC-2** 행 추가·셀 편집·행 삭제를 지원하고, 편집 상태 표기는 Data 그리드 관례와 같다 — 신규행 `NEW` 배지, 삭제행 취소선, 변경 셀 하이라이트.
- **AC-3** 짝짓기 기준 값이 비었거나 다른 행과 겹치면 그 행을 오류로 표시하고 이유를 알린다(기준 값 중복 금지).
- **AC-4** NULL 토글을 제공하고 NULL 은 흐린 이탤릭으로 표기한다(Data 뷰와 같은 표기).
- **AC-5** 컬럼 폭은 Data 그리드의 자동 폭 로직(`console/data/colWidth`)을 재사용한다 — 같은 계산을 두 번 만들지 않는다.
- **AC-6** 이 화면은 **실 DB 를 건드리지 않는다** — 저장은 로컬 설계 저장소에만 일어나고 어떤 DDL·DML 도 실행하지 않는다.
- **AC-7** 컬럼 머리는 그 컬럼의 **제약을 그 자리에서** 보인다: `PK`·`FK`·`UK`·`IDX` 텍스트 배지(복합 제약은 위치 번호 — `UK1`·`UK2`), CHECK 참여 컬럼은 `CHK`, 시드가 반드시 채워야 하는 컬럼은 `필수`. 마우스를 올리면 상세(타입 · NULL 허용/불가 · 기본값 또는 자동증가 · **FK 참조 대상과 정책** · CHECK 식 · 설명)를 한 번에 보인다 — 컬럼을 확인하려고 Definition 화면과 왕복하지 않게. 파생 로직은 Definition 정본(`derive`·`fkPolicy`)을 재사용한다.
- **AC-8** `필수`(NOT NULL + 기본값 없음 + 자동증가 아님)인데 **비어 있는 셀은 그 자리에서** 표시하고, 행 경고에 무엇이 비었는지 합쳐 알린다(짝짓기 기준 문제와 동시에 있으면 둘 다). 자동증가·기본값 있는 컬럼은 비워도 문제가 아니고, 변수 자리표시자는 **채운 것으로 본다**(값은 반영할 때 들어온다).
- **AC-9** **무시 컬럼 감추기** 토글 — `무시` 역할 컬럼을 표에서 빼고 볼 수 있다. 규칙:
  - **보기 설정일 뿐 선언이 아니다.** 세트 선언(`ignoredColumns`)은 그대로이고, 감춘 컬럼도 비교·반영에서는 계속 빠진다(무시 역할 그대로). 설계에 저장하지 않고 **세션 동안만** 유지한다 — 내 화면 편의이지 팀과 공유할 계약이 아니다.
  - **검증은 감춘 컬럼까지 본다.** 감춘 컬럼의 필수 빈 칸·깨진 참조·짝짓기 기준 문제는 행 경고에 그대로 나온다 — 보기 설정이 "무엇을 문제로 볼지"를 바꾸면 안 된다(감추면 오류가 사라지는 화면은 거짓말을 한다).
  - 감출 컬럼이 없으면 토글을 내지 않는다(누를 게 없는 버튼을 두지 않는다). 개수는 **설계에 실제로 있는** 무시 컬럼만 센다.
  - 켠 상태에서는 그 컬럼의 역할 토글도 안 보인다 — 역할을 되돌리려면 먼저 다시 보이게 해야 한다는 것을 버튼 설명이 알린다.
- **AC-10 (선언 바는 개수로 말한다)** 선언 바의 무시 컬럼은 **개수만** 보인다(`무시 6`). 이름을 다 늘어놓으면 컬럼이 몇 개만 돼도 선언 바가 컬럼 목록에 잡아먹혀 정작 중요한 선언(짝짓기 기준·PK 획득·설계에 없는 행)이 묻힌다. 어느 컬럼인지는 마우스를 올리면 보이고, 표에서도 흐리게 그려져 이미 구별된다 — 같은 정보를 두 곳에서 두 번 말하지 않는다.
  - **읽기 전용(커밋 버전 열람)에서도 쓸 수 있다** — 보기 설정은 편집 권한과 무관하다. 이때 그리드 도구줄에는 행 수와 이 토글만 나온다(행 추가·세트 삭제는 없다).

### Section db-design.seed.variables — 변수 자리표시자 (환경차 분리)
- **AC-1** 셀 값이 `{{이름}}` 꼴이면 **변수**로 알아보고 셀에 변수 표식을 보인다. 문법은 저장쿼리 파라미터화와 같다 — bare `{{x}}` 만 변수, `'{{x}}'`(따옴표 안)는 리터럴.
- **AC-2** 세트 머리에 그 세트가 요구하는 변수 목록을 중복 없이 이름순으로 보인다.
- **AC-3** 변수는 **이름으로 비교**된다 — 같은 변수 이름끼리는 Diff 에서 차이가 아니다(환경차가 diff 소음이 되지 않게).
- **AC-4** 이 화면에는 변수의 **값 입력칸이 없다**. 값은 환경 쪽에 두고(비밀값은 OS 키체인 암호화 경로) 반영 시점에 치환한다 — 후속 범위. 화면은 비밀값을 평문으로 넣지 말고 변수를 쓰라고 안내한다.

### Section db-design.seed.reference — 시드 행끼리의 참조 (`@테이블#별칭`)
> 시드 행이 다른 시드 행을 가리킨다. 서러게이트 PK 는 환경마다 다르므로 값으로 가리킬 수 없고,
> 고정값을 박으면 남의 행을 덮어쓸 위험이 있다 — 그래서 **설계 안에서만 사는 이름(별칭)** 으로 가리킨다.

- **AC-1** 시드 행마다 **별칭**을 둘 수 있다. 설계 전용 이름이며 **실 DB 에 들어가지 않는다.** 비어 있어도 되고(참조 대상이 아닌 행), 같은 세트 안에서 겹치면 오류, 글자는 영문·숫자·`-`·`_` 만.
- **AC-2** 참조 표기는 **`@테이블#별칭`** 이다. 값이 진짜 `@` 로 시작해야 하면 `@@` 로 탈출하고, 반영 시 `@@x` 는 `@x` 로 되돌린다.
- **AC-3** 왜 별칭인가(짝짓기 기준 값을 그대로 쓰지 않는 이유): 기준 값(email·code)은 실제로 바뀌고, 그때 그걸 가리키던 참조가 전부 깨진다. 기본 별칭은 기준 값에서 자동 생성(`admin@acme.com` → `admin-acme-com`)하고 사람이 고칠 수 있다.
- **AC-4** 왜 문법을 도구가 정하나: ① 반영 때 실제 id 로 치환해야 하고 ② 깨진 참조를 검출해야 하고 ③ **되먹임에서 도구가 `user_id=7` 을 다시 이 표기로 되돌려 써야** 한다(③이 결정적 — 규칙이 없으면 되돌릴 수 없다). 되돌릴 때도 같은 함수(`formatSeedRef`)를 쓴다.
- **AC-5** 검증은 셀 단위로 다음을 잡는다: 표기 오타(`@` 로 시작하는데 규칙 불일치) · 시드 세트가 없는 테이블 · **없는 별칭(깨진 참조)** · FK 아닌 컬럼에 사용 · **FK 가 가리키는 테이블과 다른 대상**(문법은 맞아도 반영하면 남의 테이블 id 를 꽂는다).
- **AC-6** **순환 참조는 금지**한다 — A→B, B→A 면 어느 쪽도 먼저 넣을 수 없다. 자기 자신을 가리키는 행도 순환이다. 순환에 걸린 행을 표시한다.
- **AC-7** 참조 셀은 값 대신 참조임을 알아보게 표시하고(연결 표식), 깨진 참조는 오류로 보인다.

### Section db-design.seed.persistence — 저장
- **AC-1** 시드 세트는 **설계 스코프**로 저장된다 — 설계 X 저장이 설계 Y 의 세트를 건드리지 않는다(`tables` 와 같은 방식).
- **AC-2** 앱을 다시 켜도 세트 선언과 행이 그대로 남는다.
- **AC-3** 새로 만든 IPC 채널은 MCP 커버리지 지도(`src/main/ai/coverage/<서비스>.ts`)에 **노출 또는 제외 사유**로 등재된다(프로젝트 불변식 4).
- **AC-4** 설계를 지우면 그 설계의 시드도 함께 사라진다 — 시드는 설계 소유물이다. 남기면 같은 이름의 새 설계에 유령 시드가 붙는다.

### Section db-design.seed.apply-contract — 반영·되먹임 계약
> **구현됨** — 화면은 `Migration › Seed`(`db-migration.seed`), 계산은 순수 모듈
> `seedApplyPlan`(설계→운영) · `seedImportPlan`(운영→설계).

- **AC-1 (매칭)** 반영은 언제나 **짝짓기 기준으로 조회 → 실제 행**이다. PK 는 찾는 기준이 아니라 **찾은 결과**다. 있으면 UPDATE(PK 는 건드리지 않는다), 없으면 INSERT.
- **AC-2 (PK 획득)** 세트마다 PK 를 어떻게 얻을지 선언한다(선언 바의 `PK` 토글): `DB 가 만든다`(기본 — 시드는 PK 를 담지 않는다) / `시드가 정한다`(셀에 직접 쓰거나 **생성 규칙**으로 만든다). 규칙은 자리표시자를 쓴다 — `{uuid}`(결정적 UUID) · `{key}` · `{alias}` · `{table}`. **랜덤 생성은 없다**: 재실행마다 값이 달라져 같은 행이 두 벌 생긴다. `{uuid}` 는 설계·테이블·행 정체성에서 계산한 **이 도구의 결정적 UUID**(RFC 4122 v5 가 아니다 — 렌더러에서 동기 SHA-1 을 쓸 수 없어 자체 해시를 쓰고, 형태만 UUID 를 따르며 버전 자리는 `8`).
- **AC-2a (규칙은 쓰는 게 아니라 고르는 것)** 생성 규칙은 **고르기(드롭박스)** 로 준다. 실제로 유효한 규칙은 몇 개뿐인데 자유 문자열로 받으면 세 가지 사고가 한꺼번에 열리기 때문이다 — 오타(`{uuidd}`) · 타입 불일치(`bigint` PK 에 `{uuid}`) · **상수 규칙**(행마다 안 변해 모든 행이 같은 PK 를 받는다). 잘못 쓸 수 있게 만들고 경고를 붙이는 것보다 **고를 수 없게 하는 것**이 낫다.
  - 목록은 **PK 컬럼 타입으로 걸러** 내놓는다: 숫자·날짜·불리언·JSON PK 에는 `그리드 셀에 직접 쓴 값` 하나뿐이고, 문자 PK 에는 `{key}`·`{alias}`·`{table}-{alias}` 가, 36자 이상 담을 수 있으면 `{uuid}` 까지 나온다. **목록에 있는 규칙은 전부 행마다 값이 달라진다** — 상수 규칙은 애초에 고를 수 없다.
  - "규칙 없음"은 숨은 상태가 아니라 **목록의 첫 항목**(`그리드 셀에 직접 쓴 값`)이다 — "비우면 셀 값" 같은 암묵 규칙을 두지 않는다.
  - **`직접 입력…`** 을 남긴다 — `role-{key}` 처럼 접두사가 필요한 경우가 실제로 있다. 이 경로에서만 자리표시자 칩(누르면 규칙 끝에 붙는다)과 위 세 경고가 함께 나온다. 고르기로 끝나는 대부분의 경우엔 칩도 경고도 화면에 없다.
  - 어느 경로든 **1행에 실제로 들어갈 값**을 함께 보인다 — 고른 것이 무슨 값이 되는지가 이 화면의 설명서다. 미리보기 값은 반영 계획과 **같은 함수**로 계산한다(갈라지면 미리보기가 거짓말이 된다). 값이 아직 없어 반영이 막히는 상태, 복합 PK 일 때 규칙이 첫 컬럼에만 적용된다는 사실, PK 가 없는 테이블이라 이 선언 자체가 성립하지 않는 경우도 그 자리에서 알린다.
  - 타입 판정은 **확실한 것만** 잡는다(오탐이 나면 안내를 안 믿게 된다) — 변수 `{{이름}}` 는 반영 때 채워지므로 판정하지 않는다.
- **AC-3 (PK 는 INSERT 전용)** 시드가 PK 값을 담더라도 그것은 **새로 넣을 때 쓰는 값**이고 UPDATE 대상이 아니다. 이미 다른 id 로 존재하는 환경에서는 **PK 를 바꾸지 않고 불일치로 보고**한다 — PK 변경은 그 행을 가리키는 모든 FK 를 흔드는 파괴적 작업이라 자동으로 하면 운영 장애가 난다.
- **AC-4 (덮어쓰기 방어선)** 시드가 PK 값을 제공할 때는 반영 직전에 `그 PK 를 이미 쓰는 행의 짝짓기 기준` 을 조회해, **다른 행이 그 PK 를 쓰고 있으면 반영을 중단**한다(남의 행을 덮어쓰는 유일한 경로).
- **AC-4b (시드 행끼리의 방어선)** **시드 안에서** 두 행이 같은 PK 를 만들면 그것도 막는다. 실 DB 와의 충돌만 보면 이건 안 잡히고 — 상수 규칙이거나 셀에 같은 값을 두 번 쓰면 — 계획은 조용히 통과했다가 반영 트랜잭션에서 두 번째 INSERT 가 터진다. 겹친 행만 빼고 앞선 행은 그대로 둔다(누가 먼저 그 PK 를 주장했는지 문장에 남긴다). 규칙 목록이 상수 규칙을 안 내놓아도 이 방어선은 필요하다 — 되먹임·수동 입력·`직접 입력` 으로도 같은 값이 들어올 수 있다.
- **AC-5 (참조 해석)** 참조는 대상 행의 실제 id 로 치환하고, 삽입 순서는 참조 그래프로 위상정렬한다(순환은 저작 단계에서 이미 금지).
- **AC-6 (되먹임)** 가져올 때는 짝짓기 기준으로 행을 짝짓고, FK 컬럼 값은 참조 표기로 되돌리며, **DB 가 만드는 PK 는 설계에 담지 않는다.** 한 줄 원칙: **환경마다 달라지는 값은 설계 정본에 담지 않는다 — 담는 건 짝짓기 기준과 참조뿐.**
- **AC-7 (자동 채택 금지)** 되먹임은 후보를 만들 뿐이고 **사람이 고른 것만** 설계에 담는다 — 운영 DB 에는 설계로 올려선 안 되는 행(임시 계정·환경 전용)이 섞인다. 되돌리지 못한 참조·조회 상한에 걸린 테이블은 **반드시 알린다**(조용한 절단·조용한 실패 금지).
- **AC-8 (게이트)** 실 DB 쓰기는 전부 트랜잭션 게이트를 지난다 — `실행 → 영향 행수 확인 → 커밋/롤백`. 막는 것(blocker)이 **하나라도** 있으면 반영하지 않는다(반쯤 심고 마는 상태 금지). 삭제 후보는 기본으로 실행하지 않고 사람이 따로 켠다.
- **AC-9 (변수 값)** `{{이름}}` 의 값은 **환경 단위**로 저장하며 **OS 키체인으로 암호화**한다(연결 비밀번호와 같은 경로). 목록은 값이 아니라 "채워졌는지"만 보이고, 평문은 반영 직전 조회에서만 나온다. 값이 없으면 반영을 막는다.

### Section db-design.seed.version-diff — 버전 스냅샷·Diff
- **AC-1** 버전 컷 시 스냅샷에 시드를 함께 담는다(`{ tables, seeds }`). 컷 모달과 Timeline 의 버전 행은 **담기는/담긴 시드 행 수**를 보인다(시드가 0이면 표시하지 않는다) — 무엇이 버전에 들어갔는지 컷 직전·직후에 확인할 수 있게.
- **AC-2** 시드가 없던 **옛 스냅샷과 비교해도 깨지지 않는다** — `seeds` 없음은 빈 목록으로 읽는다.
- **AC-3** 버전 비교(Design › Versions — 타임라인에서 두 버전을 고르면 아래에 열리는 패널)에 시드 섹션이 뜬다: 세트 추가/삭제 + 행 추가/삭제/값 변경. 행 짝짓기는 **짝짓기 기준 컬럼**으로 하고 **무시 컬럼은 비교에서 뺀다**.
- **AC-3b** 행을 짝지을 수 없는 세트(짝짓기 기준 없음·양쪽 선언 불일치)는 행 delta 를 만들지 않되, 행 내용이 실제로 다르면 그 세트를 **변경 + `행 비교 불가`** 로 보인다 — "바뀐 걸 비교하지 못했다"는 사실을 침묵하지 않는다. 행 로컬 id 차이는 차이로 보지 않는다.
- **AC-4** 선언 자체의 변경(짝짓기 기준·무시 컬럼·`설계에 없는 행` 처리)도 차이로 잡는다.
- **AC-5** 스키마는 그대로고 시드만 바뀐 두 버전을 비교하면 "변경 없음"으로 보이지 않는다.

## Surface: db-design.definition (Definition 뷰 — 부분 흡수: 뷰 선언)

> 이 Surface 전체는 아직 정본 미흡수다(위 표 참조). 아래는 **뷰(view) 선언**만 명세한다 —
> Remote 는 실 DB 를 역설계해 테이블과 뷰를 갈라 보여 주는데 설계부에는 뷰라는 개념 자체가 없어
> 같은 화면이 서로 다르게 보이던 문제를 없앤 변경분이다.

### Section db-design.definition.view — 뷰 선언
- **AC-1** 사이드바 `+` 에서 **테이블 / 뷰** 중 무엇을 만들지 고른다. 이미 있는 대상은 상세 화면의 `⋯` 메뉴에서 **테이블 ↔ 뷰** 로 바꿀 수 있다.
- **AC-2** 뷰는 **본문 SELECT**(`CREATE VIEW <이름> AS` 뒷부분)를 가진다. 본문은 구조화하지 않고 설계 방언의 SQL 문자열 그대로 보관한다 — 조인·집계·윈도우까지 오는 임의 질의라 쪼개도 방언 차이를 흡수하지 못한다.
- **AC-3** 뷰의 컬럼 목록은 그 SELECT 가 내놓는 **결과 컬럼**을 사람이 적어 두는 자리다(ERD·Data 화면이 뷰의 모양을 알기 위해 필요). 실 DB 생성에 쓰이는 것은 본문 SELECT 다.
- **AC-4** 뷰에는 **제약을 걸 수 없다** — 제약 구역·키 배지·키 토글을 감추고, 테이블 → 뷰 전환 시 기존 제약은 지운다(지우기 전 확인을 받는다). Diagram 에서도 뷰 노드는 관계 핸들을 열지 않고, 뷰가 끼는 FK 드래그는 무시한다.
- **AC-5** DDL 은 `CREATE TABLE` 이 아니라 `CREATE VIEW` 로 나온다. `OR REPLACE` 는 지원하는 방언(MySQL·MariaDB·PostgreSQL)에만 붙이고 SQLite 에는 붙이지 않는다. 본문이 비면 자리만 만들고 무엇이 비었는지 주석으로 알린다. 이름은 다른 식별자와 같은 인용 이스케이프를 거친다(주입 방어).
- **AC-6** 뷰 표식(`isView`)과 본문(`viewSql`)은 로컬 저장소·IPC·MCP 왕복에서 보존된다. 버전 Diff 는 **테이블 ↔ 뷰 전환**과 **본문 변경**을 각각 차이로 잡는다 — 컬럼·제약만 보면 조용히 지나간다.
- **AC-7** 시드 세트는 뷰를 대상으로 만들 수 없다(뷰는 데이터를 담지 않는다) — `db-design.seed.set-list` AC-2 와 같은 규칙.

### Section db-design.definition.sql — SQL(DDL) 카드 (Design·Remote 공용)
> 정본 컴포넌트: `workspaces/definition/SqlCard`. 설계부(`SqlForm`)와 운영부(`remote/definition/SqlView`)는
> 이 카드를 감싸기만 한다 — 한쪽에서 DDL 이 다르게 보이면 같은 것을 두 번 만든 셈이다.
- **AC-0** **이름을 다 알면 스키마 한정 이름을 쓴다 — 하나뿐이어도.** (2026-08-11 사용자 결정으로 규칙이 바뀌었다. 예전엔 "둘 이상일 때만"이었는데, 그러면 나간 문이 `ALTER TABLE \`users\`` 라 **어느 데이터베이스에 떨어지는지가 그때 `USE` 된 DB 에 달린다** — 엉뚱한 DB 에 반영되는 길이다. 목적지는 SQL 자체에 적혀야 한다.) 목록에 **스키마를 모르는 표가 하나라도 섞이면 안 붙인다** — 반쯤 한정된 SQL 은 일부를 명시된 DB 로, 나머지를 세션의 DB 로 흩는다. SQLite 는 붙일 층이 없어 언제나 안 붙인다. 판정 정본: `db/schemaCatalog.shouldQualify`. 같은 규칙이 반영 계획(Migration)에도 적용된다.
- **AC-0a** 전체 스크립트는 한정 이름을 쓸 때 **스키마를 먼저 만든다** — PostgreSQL `CREATE SCHEMA IF NOT EXISTS`, MySQL `CREATE DATABASE IF NOT EXISTS`. **PostgreSQL 의 `public` 만** 건너뛴다(새 데이터베이스에 언제나 있다). MySQL 계열엔 "언제나 있는 이름"이 없으므로 선언한 DB 는 모두 만든다 — 예전엔 `public` 을 그 자리로 착각해 MySQL 에서도 건너뛰었다. SQLite 는 아무것도 안 붙인다.
- **AC-1** 카드 머리의 범위 토글(`이 테이블` / `전체 N`)로 보는 범위를 바꾼다. `전체` 는 **스키마 전부를 한 스크립트**로 낸다 — 위에서 아래로 그대로 실행하면 스키마가 서야 하므로 **FK 의존 순서로 정렬**하고(참조당하는 테이블이 먼저, 뷰는 맨 뒤), 정렬로 못 푸는 고리(서로 참조)는 한쪽 FK 를 `CREATE` 에서 빼고 끝에서 `ALTER TABLE … ADD CONSTRAINT` 로 건다. SQLite 는 정방향 참조가 되고 `ADD CONSTRAINT` 자체가 없으므로 미루지 않는다. 정본: `workspaces/definition/schemaScript.ts`.
- **AC-2** 목록에서 테이블을 고르면 범위는 `이 테이블` 로 돌아온다 — 고른 것이 안 보이면 "안 먹었다"로 읽힌다.
- **AC-3** `Copy` 는 보이는 것을 그대로 클립보드에, `저장` 은 같은 것을 `.sql` 파일로 내려받는다. 파일 이름은 테이블 범위면 테이블 이름, 전체 범위면 **설계 이름(운영부는 연결 이름)** 이고 파일 이름에 못 쓰는 글자는 걸러진다(`sqlFile.ts`).
- **AC-4** 상세 서랍·크게 보기처럼 이름이 바로 위에 이미 보이는 자리에서는 카드 머리를 되풀이하지 않고(`labeled=false`) 범위 토글도 두지 않는다 — 그 자리는 테이블 하나를 다루는 자리다.
- **AC-5** 이 카드에 **편집 단추를 두지 않는다.** DDL 은 Table 폼에서 파생되는 **생성물**이라 손댈 것이 없다 — 설계부에 있던 `Format` 은 그래서 뺐다(누를 것이 있는 것처럼 보이지만 정렬할 원문 자체가 없다. 2026-07-30 사용자 지시).

### Section db-design.definition.schema — 설계 테이블의 스키마
> 실 DB 를 그대로 옮겨 담으려면 설계도 여러 스키마를 가져야 한다(§db-remote.scope R4).
>
> **기본 스키마 이름은 방언마다 다르다** (2026-08-11 사용자 지적으로 바뀜). 예전에는
> `db/schemaRef` 의 `DEFAULT_SCHEMA = 'public'` 하나를 방언과 무관하게 썼다. 그런데 `public` 은
> **PostgreSQL 의** 기본 스키마 이름이라 MySQL 서버에는 그런 데이터베이스가 없다 — MySQL 설계가
> 존재하지 않는 이름을 들고 있었고, 그 상태로는 Migration 이 `(스키마, 이름)` 으로 짝을 하나도
> 못 찾아 "실 DB 전부 삭제 + 설계 전부 신규"를 계획할 수 있었다. 정본 값은
> `db/schemaCatalog.suggestSchemaName(dialect, designName)` 이고, 설계가 실제로 든 이름은
> **`design.declaredSchemas`** 에 남는다.
>
> **층 맞춤**: PostgreSQL 의 `schema` 와 MySQL 의 `database` 는 **같은 자리**다 — 한 서버 안에
> 여럿 있고, 연결 하나가 자유롭게 넘나들며 조인·FK 도 건다. 하나 늘리는 무게도 같다. PostgreSQL
> 에만 그 **위층**(database)이 하나 더 있는데 그건 연결을 갈아타는 층이라 여기서 다루지 않는다.
> 그래서 pg·mysql·mariadb 는 한 모델이고, 층 자체가 없는 sqlite 만 예외다(`supportsSchemas`).
- **AC-1** 테이블은 스키마를 갖는다. 저장소에서 읽을 때 **안 적힌 행은 안 적힌 채로 둔다** — 이름을 지어내지 않는다. 빈 스키마는 `db/schemaRef` 가 "같은 스키마"로 다루고, 실 DB 와 견줄 때는 `versions/align` 이 이름만으로 짝을 찾아 실 DB 쪽 스키마를 물려받는다.
- **AC-2** 상세 머리에서 스키마를 이름 앞 칸으로 고친다(`testdb` **.** `users`). 비워 커밋하면 "이름 없음"이 되고 `.` 도 안 찍힌다.
- **AC-3** 교차 스키마 FK 를 설계 안에서 그린다 — 참조 해석은 `db/schemaRef` 가 정본(`db-remote.scope` AC-5 와 같은 규칙).
- **AC-4** 버전 Diff 는 **스키마 이동을 차이로 잡는다**(`참조 스키마` 항목 포함) — 이름이 그대로인데 스키마만 바뀌면 조용히 다른 테이블을 가리키게 된다.
- **AC-5** **새로 만드는 표·뷰도 스키마를 갖고 태어난다** — ⑴ 범위를 골랐으면 그 첫 스키마(= 지금 보고 있는 자리), ⑵ 아니면 **설계가 선언한 첫 스키마**(`declaredSchemas[0]`), ⑶ 선언이 없고 이 설계가 쓰는 스키마가 하나뿐이면 그것, ⑷ 그래도 못 정하면 **방언의 기본값**(`suggestSchemaName`). sqlite 는 층이 없어 빈 이름이다. 판정 정본은 `definition/designScope.newTableSchema`.
- **AC-6 (신설 2026-08-11)** **설계 단계에서 스키마를 만들고 이름을 고치고 지운다** — 설계 손잡이의 `스키마 관리`(MySQL 계열은 `데이터베이스 관리`). 이것이 없던 동안 스키마를 적는 곳은 표마다 있는 자유 입력 칸 하나뿐이라 **표가 없는 스키마를 만들 방법이 아예 없었고, 실 DB 를 가져오지 않으면 설계를 시작할 수 없었다**(사용자: "실제 DB가 물려야 설계를 할 수 있는 치명적인 기능 막힘"). 정본: `designs/SchemasDialog` · 규칙은 `db/schemaCatalog`.
  - 목록은 **선언한 것 + 표에서 발견된 것**을 합쳐 보인다(`resolveSchemas`) — 한쪽만 보면 방금 만든 빈 스키마나 가져온 스키마가 사라진다. 첫째가 새 표가 태어날 자리라 `기본` 배지를 단다.
  - **이름 바꾸기는 그 스키마의 표 전부를 옮긴다**(`definition/store.moveSchema`). 표의 `id`(`t:public.users`)는 그대로 둔다 — 다시 매기면 제약의 컬럼 참조까지 줄줄이 갈아야 하고, 실 DB 와 견줄 때는 `align` 이 (스키마, 이름)으로 id 를 다시 계산하므로 낡은 id 가 비교를 틀리게 하지 않는다.
  - **표가 남아 있는 스키마는 지울 수 없다** — 표가 갈 곳이 없어지면 목록에서 조용히 사라진다.
  - **이름 없는 표**가 있으면 목록 아래에 그 개수와 "○○ 로 옮기기"를 보인다 — 선언 기능 이전 데이터를 거두는 길이고, 감추면 그 표는 한정 이름을 못 받아 계획이 세션 상태에 기댄다.
  - **AC-6a** MySQL/MariaDB 설계가 `public` 을 들고 있으면 그 창에서 **경고하고 이름을 고치라고 말한다**(`schemaIssues`) — 옛 기본값이 방언을 안 보고 채운 흔적이라 앱이 낸 손해다. 조용히 두면 Migration 이 짝을 못 찾는다.
- **AC-7 (신설 2026-08-11)** **새 설계 모달이 첫 스키마 이름을 받는다** — 벤더를 고른 뒤 뜨고(sqlite 는 안 뜬다), `suggestSchemaName` 값이 **미리 채워지되 고칠 수 있다**. 설계 이름을 그대로 규칙으로 삼지 않는 이유: ⑴ 설계 이름은 사람이 읽는 라벨이라 식별자로 못 쓸 글자가 흔하고(MySQL 의 DB 이름은 디스크 폴더 이름이 되어 `/ \ .` 금지·64자 상한), ⑵ **설계 이름을 나중에 바꿔도 스키마 이름은 안 따라가야 한다**(그건 데이터가 딸린 DDL 이다). 그래서 처음부터 칸을 가른다.
  - **왜 못박는가**: 목록·다이어그램은 범위로 거를 때 `스키마가 있고 && 고른 범위에 든다` 를 요구한다(`db/scope.scopedTables`). 만드는 쪽에만 기본값이 없던 동안 새 표·뷰는 스키마 없이 태어나, 범위를 켠 설계에서는 **`테이블 추가`·`뷰 추가` 를 눌러도 저장만 되고 화면엔 아무것도 안 떴다**(2026-08-04 사용자 제보 · 실측 재현). 앱을 다시 열면 AC-1 의 폴백이 채워 그제서야 나타났다 — 만들기와 불러오기가 같은 기본값을 써야 한다.

### Section db-design.definition.side-panel — 사이드 패널 (Design·Remote 공용)
> DB 서비스의 왼쪽 패널은 **속(목록)과 겉(바깥 틀)이 모두 공용**이다. 2026-08-04 이전엔 겉이 세 갈래로
> 갈라져 있었다(크기 조절 패널 / 240px 고정 / 224·288px 고정) — 같은 서비스인데 화면을 옮길 때마다
> 왼쪽이 다르게 생겼다는 사용자 지적으로 하나로 모았다.
- **AC-1** Design·Remote 의 **여섯 화면**(Design › Definition·Diagram·Seed, Remote › Definition·Diagram·Data)이 같은 바깥 틀(`shell/WorkspacePanels`)에 목록을 담는다: 머리줄(이름 + 동작) · **끌어서 폭 조절** · 접기/펼치기.
- **AC-2** 목록 자체는 **하나의 공용 컴포넌트**(`db/TableSidePanel`)를 쓴다. 담는 것이 테이블이 아닌 화면(Seed 의 시드 세트)도 **행·구역 머리·빈 상태는 같은 부품**(`db/sideList`)으로 그린다 — 클래스 문자열을 화면마다 베껴 두면 한쪽만 고쳐져 조용히 어긋난다.
- **AC-3** 패널은 `테이블·뷰` / `제약` 두 탭을 가진다(Diagram 은 `그룹` 탭을 하나 더 둔다). 탭 이름이 `테이블` 이면 바로 아래 구역 머리(`테이블 4`·`뷰 1`)와 개수가 어긋나 보이므로 **둘을 다 말한다**. `테이블·뷰` 탭은 테이블과 뷰를 **구역으로 갈라** 각 구역의 개수를 보인다.
- **AC-4** `제약` 탭은 종류 필터(`ALL`·`PK`·`FK`·`UK`·`IDX`·`CHECK`, 각 개수 표시)와 **테이블별 그룹**으로 제약을 보인다. 항목을 누르면 그 제약이 걸린 테이블로 이동한다(Diagram 에서는 그 노드로 화면이 이동).
- **AC-5** **접기/펼치기.** 머리줄의 접기 손잡이로 패널을 접으면 좁은 세로 띠(아이콘 + 세로 제목)만 남고 본문이 그만큼 넓어진다. 띠를 누르면 접기 전 폭으로 돌아온다. 접힌 상태는 **화면마다 따로** 저장된다(`autoSaveId`).
  - 접혀도 패널 내용은 **DOM 에 남긴다** — 검색어와 고른 탭이 유지되도록. 대신 안 보이는 동안 Tab 키·읽어주기 대상에서 뺀다(`inert`).
  - 이 손잡이는 DB 만의 것이 아니다 — 같은 부품을 쓰는 **UI/UX · API · AI 의 사이드바에도 켜져 있다**(2026-08-04). 부품 차원의 기능이므로 서비스마다 다르게 두지 않는다.
- **AC-5a** **오른쪽 패널이 있는 화면**(Remote › Query 의 `Schema`, Remote › Collection 의 `Queries`)은 왼쪽·오른쪽을 **각각** 접고, **양쪽을 한 번에** 여닫는 손잡이를 하나 더 둔다.
  - 그 양쪽 손잡이는 **네 자리 모두**(양쪽 머리줄·양쪽 띠)에 같은 모양으로 선다. 한 곳에만 두면 그 패널이 접히는 순간 손잡이도 같이 사라져 되돌릴 방법이 없어진다.
  - 오른쪽 패널을 여닫는 별도 버튼을 본문에 두지 않는다 — 패널의 접기 손잡이와 세로 띠가 그 일을 한다(같은 일을 하는 손잡이 둘 금지). Query 의 옛 `Schema` 토글 버튼이 그래서 없어졌다.
- **AC-6** 집계·정렬·필터는 순수 로직(`db/remote/constraintsView`·`db/tableList`)이 하고 패널은 그리기만 한다 — 같은 계산을 두 번 만들지 않는다.
- **AC-7** 빈 상태는 **명사구 한 줄**이다(`테이블 없음`·`검색 결과 없음`·`시드 세트 없음`). 사용법을 덧붙이지 않는다(서비스 문구 규칙).

## Surface: db-design.diagram (Diagram 뷰 — 부분 흡수: 공용 시각 레이어 참조)

> 설계의 **가상 ERD**. 배치 영속·그룹(레이어)·상세보기 서랍은 Remote › Diagram 과 **같은 코드·같은 규칙**이라
> 정본을 두 벌 두지 않는다 — `db-remote.diagram` 의 아래 절이 이 화면에도 그대로 적용된다:
> `db-remote.diagram.layout` · `.group` · `.group-panel` · `.detail`.

### Section db-design.diagram.scope — 설계 스코프 (Design 만의 차이)
- **AC-1** 배치·그룹의 저장 스코프는 **설계별**이다(키 `design:<설계 id>`). 설계를 바꾸면 그 설계의 배치·그룹이 뜬다.
- **AC-2** **커밋된 버전을 보는 중(읽기 전용)에는 배치·그룹을 저장하지 않는다** — 지나간 버전의 화면을 만졌다고 정본이 바뀌면 안 된다.
- **AC-3** 상세보기 서랍의 내용은 설계 편집 폼(`TableForm`)이다 — Design › Definition 에서 되는 편집이 다이어그램에서도 그대로 된다. 이 서랍이 예전의 좁은 우측 편집 패널을 **대체**한다(같은 편집을 두 자리에서 다르게 하지 않는다).
- **AC-4** **고른 표는 Definition ↔ Diagram 을 오가도 유지된다** — 둘이 `useDefinitionStore.activeTableId` 하나를 함께 본다(2026-08-04 사용자 요청). 다만 여기 들어올 때 상세 서랍이 저절로 열리지는 않는다 — 서랍은 **누른 순간**만 연다. 빈 캔버스를 눌러 고름을 풀면 Definition 도 함께 풀린다(그 경우 목록 첫 표로 폴백). 운영부도 같은 규칙이다(`db-remote.definition.table-list` AC-7).
