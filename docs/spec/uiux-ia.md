# Service: uiux (UI/UX — 화면·디자인 설계)

> 제품의 **화면과 그 규칙을 설계하는 자리**. 코드를 만들지도, 구현이 설계대로인지 판정하지도 않는다 —
> 설계의 정본을 들고, 사람과 에이전트(= AI 코딩 도구)가 **같은 데이터**를 읽고 고치게 한다.
> 위계: Project > Application > Service > Surface > Section > Component.
> 원형은 `gems/flare`(Intuvibe Studio) 의 Plan 부서 — 가져온 것과 뺀 것은 §7.

## 이 문서의 범위 (정본 흡수 현황)

`docs/spec/README.md` 흡수 원칙에 따라 **steward spec 단계를 거친 Surface 부터** 점진적으로 채운다.

| Surface | 상태 |
|---|---|
| `uiux.shell` | **이 문서에 명세됨** — nav 골격(모듈·뷰·컨텍스트 셀렉터) |
| `uiux.screens.spec` | **이 문서에 명세됨** — 위계 편집 + 화면 구조 편집 |
| `uiux.screens.canvas` | **이 문서에 명세됨** — 미리보기 + 끌어놓기 편집 |
| `uiux.features` | **이 문서에 명세됨** — 능력 인덱스 + 완성 상태 |
| `uiux.screens.review` | **이 문서에 명세됨** — 요소에 붙는 의견(핀) |
| `uiux.style` | **이 문서에 명세됨** — 디자인 토큰 + 컴포넌트 매트릭스 |
| `uiux.flows` | **이 문서에 명세됨** — 화면 사이 흐름 그래프 |
|  `uiux.flows` · `uiux.rules` · `uiux.style` · `uiux.versions` | **미구현(placeholder)** — 경로 배지만. 각 Surface 의 인수조건은 그 화면을 짓는 단계에서 이 문서에 추가한다 |

화면이 아닌 것 중 구현된 것: **§7 데이터 모델** — 저장소 스키마(`store/migrations/uiux.ts`), 도메인 타입
(`services/uiux/types.ts`), 안정 주소(`address.ts`), 화면 내용 방어 파싱(`content.ts`). 저장 경로(IPC·preload)는
Screens 를 지을 때 함께 만든다 — 쓸 곳 없는 통로를 미리 뚫지 않는다.

## 1. 정체 — 하는 일과 안 하는 일

**하는 일**

- 화면 설계의 정본을 든다 — 구조(무엇으로 이루어졌나) · 흐름(누르면 무슨 일이 나나) · 규칙(어떤 값이 유효한가) · 스타일(디자인 토큰).
- 사람은 화면으로 편집하고, 에이전트는 MCP(= 에이전트가 앱의 데이터를 도구로 읽고 쓰게 하는 연결 규격)로 같은 데이터를 읽고 쓴다.
- 설계가 어디까지 구현·확인됐는지 **상태를 모아 보인다**.

**안 하는 일**

- 코드를 만들지 않는다.
- 구현이 설계대로인지 **스스로 판정하지 않는다.** UI 적합성은 기계로 가르기 어렵고, 판정에 필요한 것은 실제 코드베이스인데 그것을 아는 주체는 rockury 가 아니라 **그 코드베이스에서 일하는 에이전트**다.

> 정본이 둘로 갈린다: **의도의 정본 = 이 서비스의 설계 데이터**, **실재의 정본 = 코드.**
> 둘을 화해시키는 일은 양쪽을 다 보는 에이전트가 하고, 이 서비스는 그 **결과를 받아 적는다**(§6).

## 2. 위계 — 6층

```
Project      쿠팡 · 배민 …                       — 한 제품 전체
└─ Application  서비스 관리자 앱 · 판매 관리자 앱 · 이용자 앱   — 독립적으로 배포되는 앱
   └─ Service   로그인 · 상품 관리 · CS 관리                — 앱을 이루는 업무 묶음
      └─ Surface  로그인 화면 · 상품 관리 화면               — 진입점(화면 한 장)
         └─ Section  사용자 정보 입력 영역 · 프로필 영역      — 선택 계층(그룹)
            └─ Component  아이디 입력칸 · 로그인 버튼        — 실제 UI 조각
```

- **Project 는 원형(flare)에 없던 층이다.** flare 는 프로젝트 폴더에서 서버를 띄우는 방식이라 프로세스 자체가 프로젝트였다. rockury 는 **배포되는 데스크탑 앱**이라 그 수가 통하지 않는다 — 데이터 층으로 올린다.
- **Section 은 선택**이다. 가벼운 화면은 Section 없이 Component 를 바로 둔다. Section 이름은 관리용이며 화면에 반드시 보이지는 않는다.
- **모달·드로어는 Section 이 아니라 Surface 다.** 자기 Section 과 Component 를 갖는 컨테이너이므로 화면과 동급이다. "로그인 화면 안의 비밀번호 찾기 모달"은 형제 Surface.
- **Surface 는 화면만이 아니다**(원형에서 가져온 일반화) — 명령줄 커맨드·정해진 시각에 도는 작업(cron)처럼 **바깥 세계가 시스템에 닿는 단위**를 같은 모델로 다룬다. v1 은 화면 종류부터 채우고 나머지는 종류 값만 늘린다.

### 이름 충돌 주의 — 두 개의 "Service"

| 말 | 가리키는 것 |
|---|---|
| **rockury 서비스** | 좌측 레일의 칸 — `uiux` · `api` · `db` · `infra` · `ai` |
| **설계 대상의 Service** | 위계 3층 — 로그인 서비스, 상품 관리 서비스 … |

주소 체계도 둘이다. 섞으면 코드·테스트 대조가 깨진다.

| 무엇 | 주소 | 예 |
|---|---|---|
| **이 서비스 자신의 화면**(rockury 화면) | `uiux.<모듈>[.<뷰>]` | `uiux.screens.spec` |
| **설계 대상 화면**(사용자가 그리는 것) | `<project>.<application>.<service>.<surface>` | `coupang.buyer.auth.login` |

설계 대상 주소는 **프로젝트 안에서 전역 유일**하다 — 그래야 앱을 가로지르는 흐름(판매자 앱 등록 → 관리자 앱 승인 → 이용자 앱 노출)이 하나의 사슬로 이어진다.

## 3. 세 축 — 겹치지 않는다

| 축 | 묻는 질문 | 어디 사나 | 보는 모듈 |
|---|---|---|---|
| **구조** | 무엇으로 이루어졌나 | 포함 트리(§2) | Screens |
| **흐름(Event)** | 누르면 무슨 일이 나나 | Component 에 걸린 화살표 | Flows |
| **규칙(Rule)** | 어떤 값이 유효하고 언제 켜지나 | Component 에 붙되 위 계층에서 흘러내림 | Rules |
| **조건(when)** | 보이나 안 보이나 | Component·Section 자체의 칸 | (각 화면) |

### Event — 트리거 하나 + 효과 여럿

```
트리거 :  사용자 (컴포넌트 + 동작)     예) 로그인 버튼 · 클릭
          자동   (스케줄)              예) 매일 02:00
효과   :  화면 전이   이동 / 열기 / 닫기        → 어느 화면으로
          데이터 변이 생성 / 수정 / 삭제        → 어느 계약(상품·주문…)
```

**한 트리거에 효과가 여럿 달린다**(둘 다 가질 수 있다). 원형은 처음에 "화면 흐름"과 "데이터 흐름"을 대등한 두 갈래로 나눴다가 폐기했다 — 삭제 버튼 한 번이 *모달을 닫고* + *상품을 지우는데*, 갈래를 나누면 같은 클릭이 두 군데로 찢어진다. 같은 함정을 반복하지 않는다.

**Event 는 위계의 7번째 층이 아니다.** 출발은 한 Component, 도착은 다른 Surface 라 포함 트리 안에 담기지 않는 **화살표**다. 그래서 트리(Screens)와 그래프(Flows)를 나눈다.

### Rule — 위에서 흘러내린다

값 제약(형식·길이) · 검증 피드백(언제·어떻게 알리나) · 활성 조건(언제 버튼이 켜지나). Global → Application → Service → Component 순으로 흘러내리고 아래가 위를 덮는다. 한 컴포넌트의 **최종 규칙 + 그게 어디서 왔는지(출처)** 를 함께 보여야 한다 — 출처가 없으면 "왜 이 규칙이 여기 붙었나"를 추적할 수 없다.

## 4. nav — 모듈 6 + 컨텍스트 3

### 컨텍스트 셀렉터 (상단 바 · 화면 계층이 아니라 "무엇을 기준으로 볼지")

| 셀렉터 | 값 | 비고 |
|---|---|---|
| **Project** | 쿠팡 · 배민 … | 런타임 데이터. 바꾸면 서비스 전체가 갈린다 |
| **Version** | Draft(편집 중) / v0.4.0 … | 설계 스냅샷. DB 서비스와 동형 |
| **Viewport** | PC · 태블릿 · 모바일 | 같은 화면의 **다른 렌즈** |

- **Application 은 셀렉터가 아니다.** 전역으로 올리면 앱을 넘나드는 흐름이 끊긴다(§2). Screens·Flows 화면 **헤더의 필터**로 둔다 — 기본은 전체, 좁히고 싶을 때 좁힌다.
- **Viewport 는 화면을 세 벌 만드는 것이 아니다.** 한 Surface + 뷰포트별 덮어쓰기다. 세 벌로 만들면 정합성이 즉시 무너진다. 덮어쓰기 구조는 디자인 토큰의 base ⊕ override 와 같은 모양이라 비교·검증이 그대로 따라온다.
  - **지금 구현된 것은 폭까지다.** 뷰포트를 바꾸면 미리보기 폭이 바뀌고, 배치가 그 폭에서 어떻게 접히는지 볼 수 있다. **덮어쓰기 자체(뷰포트별로 배치를 다르게)는 모델(`content.viewports`)에 자리만 있고 편집·반영이 없다** — 실제로 좁은 화면을 여럿 그려 본 뒤 무엇을 덮어야 하는지 보일 때 채운다.

### 모듈 · 뷰

| 모듈 | 뷰 | 무엇 |
|---|---|---|
| **Features** | — | 제품 한 줄 + 능력 인덱스(앱 › 서비스 › 화면) + 능력별 완성 상태. **기본 진입** |
| **Screens** | Canvas · Spec · Review | 화면 짓기(1급) · 구조 편집 · 화면 위 핀 코멘트 |
| **Flows** | — | 이벤트 그래프 |
| **Rules** | — | 값 제약·검증·활성 + 출처 |
| **Style** | Tokens · Components | 디자인 토큰 · 컴포넌트 상태 매트릭스 |
| **Versions** | Timeline · Diff | 스냅샷 · 비교 |

**Features 가 첫 칸인 이유**: ① 새 데이터를 거의 안 만든다(트리는 화면들에서 도출, 화면 설명은 각 화면 스펙 안에 산다 — 고유 데이터는 능력 수준 설명 하나뿐) ② 상태 집계의 뼈대다("화면 42개 중 31개 확인"은 아무 그림도 안 그려지지만 "결제: 화면 5 · 확인 5 ✅ / 배송: 3 · 0 ⚠"은 읽힌다) ③ 사람과 에이전트 양쪽의 목차다.

제품 소개는 별도 모듈 없이 **Features 화면 맨 위 헤더**로 접는다.

**구획(area)을 나누지 않는다.** DB 서비스는 설계부/운영부로 갈리지만 이 서비스는 **전부 설계부**다.

## 5. 정본 저장 — 로컬 DB

설계 데이터의 정본은 **rockury 로컬 저장소**(`uiux_` 접두어 테이블)다. 프로젝트 폴더의 파일이 아니다.

**근거**

- rockury 는 **배포되는 데스크탑 앱**이다. 사용자 파일시스템 어딘가를 정본으로 삼으면 폴더 선택·쓰기 권한·외부 편집 감시·파일 이동 시 끊긴 참조가 전부 제품 문제가 된다.
- "파일이어야 에이전트가 읽는다"는 **여기서 성립하지 않는다** — rockury 는 MCP 서버를 내장하고 있어 에이전트가 도구로 직접 읽고 쓴다. DB 서비스의 설계가 이미 그렇게 돌고 있다.
- DB 서비스가 이미 로컬 저장소를 쓴다. UI/UX 만 파일로 가면 **한 앱에 저장 모델이 둘**이 되고, 그게 가장 나쁘다.

**형상 관리(git diff·PR 리뷰)는 내보내기로 산다.** 정본은 DB, 파일은 사용자가 누를 때 나오는 산출물이다 — DB 서비스가 DDL 을 뽑는 것과 같은 구조이고, 저장 대화상자로 쓰므로 권한 문제도 없다. **(아직 미구현 — 방향만 확정)**

## 6. 화면 편집 모델 — 구조가 데이터, 조작은 캔버스

Figma·Miro 가 자유 배치인 것은 산출물이 각각 **그림**과 **사고의 배치**이기 때문이다. 이 서비스의 산출물은 **명세**이고 주 소비자는 에이전트다 — 축이 다르다.

**자유 배치를 택하면 이 서비스가 풀려던 문제가 그대로 돌아온다.** 에이전트가 화면을 정확히 못 읽는 이유가 바로 `x:340, y:180, w:200` 짜리 사각형에서 "로그인 폼의 두 번째 입력칸"을 **되짚어야** 하기 때문이다. 되짚기는 틀린다.

**뷰포트 결정이 이미 자유 배치를 배제했다**(§4) — 절대 좌표로 그리면 뷰포트마다 좌표를 세 벌 찍어야 하고, 그건 "세 벌로 만들면 정합성이 무너진다"며 거부한 것이다. 실제 브라우저도 절대 좌표로 그리지 않는다.

| | |
|---|---|
| **저장되는 것** | 구조뿐 — 세로 스택 / 가로 배열 / 격자 + 순서 + 간격. **좌표 없음** |
| **조작하는 법** | 캔버스에서 끌어놓기. 놓는 순간 "이 섹션의 3번째"로 해석된다 |
| **보이는 것** | 드롭 가이드(어디 들어갈지 보여주는 선) + 실제 렌더된 화면 |

참고할 도구는 Figma 가 아니라 **Webflow · Framer · Plasmic** 이다 — 같은 문제(시각적으로 편집하되 결과는 구조)를 이미 푼 쪽이다. Figma 자신도 Auto Layout(= 자식을 가로·세로로 자동 정렬하는 컨테이너)을 도입했다.

- **예외 — Flows 그래프**: 노드 위치에 뜻이 없으므로 자동 배치하고 **위치를 저장하지 않는다**(화면이 늘어도 그래프가 알아서 정리된다).
- **경계**: 초기 발상 스케치(자유 낙서)는 이 서비스의 몫이 아니다. 종이·화이트보드가 할 일이고, 여기는 그다음 단계인 명세화를 맡는다.

### 미리보기 렌더

컴포넌트 종류마다 HTML+CSS 조각을 두고 디자인 토큰을 CSS 변수로 주입한다. 조각에는 **조건문·스크립트를 넣지 않는다** — 결정적이고 안전하며, 특정 프레임워크에 묶이지 않는다. 문법은 셋뿐이다:

```
{{label}} · {{props.placeholder}}             값 넣기
{{#props.required}}…{{/props.required}}       있으면 보이기
{{#props.options}}…{{.}}…{{/props.options}}   배열이면 반복
```

변형·상태는 **마크업이 아니라 CSS 가 가른다** — `data-variant="{{props.variant}}"` 를 두고 `[data-variant=outline]` 로 받는다. 그래야 마크업이 슬롯까지만 남는다.

**세 가지 규율**(테스트가 강제한다):

- **색·길이는 토큰 변수로만.** 하드코딩하면 사용자가 토큰을 바꿔도 안 따라오고, 그 순간 토큰의 뜻이 사라진다. 검사기가 조각 CSS 에서 리터럴을 찾아 실패시킨다.
- **조각이 쓰는 토큰은 실제로 있어야 한다.** 없는 변수를 쓰면 그 스타일이 조용히 안 먹는다.
- **값이 없어도 그려진다.** 막 만든 컴포넌트는 이름표조차 없다.

**격리는 그림자 뿌리(Shadow DOM)**. 앱은 Tailwind 전역 CSS 위에 서 있어서 조각의 `.c`·`.f` 같은 셀렉터가 양쪽을 서로 덮는다. 그림자 안은 경계가 막혀 있고 토큰만 CSS 변수로 상속돼 들어간다 — 격리와 테마가 동시에 성립하는 지점. 다만 인스턴스마다 그림자를 만들면 화면 하나에 수십 개가 생기므로, **조각별로 CSS 를 한 번만 모으고 셀렉터에 `.t-<종류>` 스코프를 붙인다**.

**모르는 종류는 대체 조각으로 떨어진다.** `type` 은 열린 문자열이라 언제든 모르는 것이 온다 — 아무것도 안 그리면 화면에 구멍이 생겨 무엇이 빠졌는지도 알 수 없다.

**원형과 다른 점**: flare 는 조각도 토큰도 하나 없이 프로젝트가 공급하게 했다(상류에 코드 생성 도구가 있었다). rockury 는 배포되는 앱이라 사용자가 빈손으로 시작한다 — **기본 조각과 기본 토큰 한 벌을 앱이 들고** 있어야 첫 화면이 그려진다. 그 위를 프로젝트 토큰이 덮는다(`uiux.style`). **조각(HTML) 자체를 덮어쓰는 것은 아직 미구현** — 지금은 앱이 든 한 벌이 전부다.

### 끌어놓기 — 좌표는 계산에만 쓰고 저장하지 않는다

화면에서 잰 사각형과 포인터 위치로 "어느 영역의 몇 번째"를 정하고 나면 **남는 것은 순서뿐**이다. 그래서 끌어 옮겨도 결과가 여전히 구조다.

- 세는 대상에서 **끌고 있는 것을 뺀다.** 그러면 나온 자리가 곧 이동 함수가 기대하는 "뽑아낸 뒤의 자리"가 된다 — 변환을 따로 두면 기준이 둘이 되어 언젠가 어긋난다.
- 세로로 쌓인 것은 위아래 중심으로 가르고, 가로·격자는 **줄부터 가른다**(좌우만 보면 아랫줄 요소가 윗줄 것보다 앞으로 판정된다).
- 미리보기는 좁은 자리에서 줄어 있는데, **잰 값도 포인터도 똑같이 화면 좌표**라 축척을 따로 나누지 않는다(나누면 오히려 어긋난다).
- 끌어놓기는 **포인터 이벤트**로 만든다. 브라우저 기본 드래그는 그림자 뿌리 경계에서 대상이 흐려지고 놓을 자리를 픽셀 단위로 정할 수 없다.

### 만드는 순서

`Spec 뷰(트리·폼)` → `미리보기 렌더` → `Canvas`. **Canvas 는 별도 캔버스가 아니라 미리보기가 편집 가능해진 것**이다. 데이터가 서야 그릴 것이 생긴다.

## 7. 데이터 모델 — 로컬 저장소

| 테이블 | 무엇 | 소속 |
|---|---|---|
| `uiux_projects` | 프로젝트 | — |
| `uiux_applications` | 앱 | project |
| `uiux_services` | 서비스 | application |
| `uiux_surfaces` | 화면 — **내용(섹션·컴포넌트·이벤트·뷰포트 덮어쓰기)은 JSON 한 칸** | service |
| `uiux_versions` | 설계 스냅샷 | project |

**왜 상위 세 층은 행이고 화면 내용은 JSON 인가**

- 상위 세 층은 목록·이름·설명이 자주 조회되고(Features 인덱스), 화면이 하나도 없어도 존재한다 — 행이어야 한다.
- 화면 내용은 트리라서 관계로 펴면 조인 지옥이 되고, **편집 단위도 버전 스냅샷 단위도 화면 하나**다. DB 서비스가 테이블의 컬럼·제약을 JSON 칸에 두는 것과 같은 판단이다.

**주소** — 각 층이 `key`(사람이 읽는 주소 조각)를 갖고, 이어 붙이면 안정 주소가 된다: `coupang.buyer.auth.login`. 프로젝트 안에서 유일하며 흐름·규칙·핀 코멘트가 전부 이 주소에 걸린다.

**상태 칸** — 화면 행이 `status`(`designed` · `implemented` · `verified`)와 확인 시각·주체·근거를 든다(§8).

**토큰·핀 코멘트 테이블은 아직 만들지 않는다** — 그 화면(Style · Screens › Review)을 지을 때 모델과 함께 정한다. 쓸 곳 없는 테이블을 미리 세우지 않는다.

### 불변식

- **INV-1** 한 프로젝트 안에서 안정 주소는 유일하다. 같은 부모 아래 같은 `key` 를 둘 수 없다.
- **INV-2** `key` 는 주소 조각이므로 **소문자 영숫자·하이픈·밑줄**만 쓰고 소문자·숫자로 시작한다. 점(`.`)을 담으면 주소를 되파싱할 때 층이 어긋나고, 공백·대문자는 주소를 흔든다. 사람이 읽는 이름은 `name` 에 따로 두므로 **한글 이름을 써도 주소는 안전하다**.
- **INV-3** 화면 내용 JSON 이 비었거나 깨져도 목록·주소·상태는 읽힌다(내용 파싱 실패가 트리 전체를 무너뜨리지 않는다).
- **INV-4** 상위 층을 지우면 그 아래가 함께 사라진다 — 부모 없는 화면은 주소를 만들 수 없어 유령이 된다.

## 8. 검증 — 판정은 에이전트, 기록은 여기

UI 가 설계대로인지는 기계로 가르기 어렵다. 그래서 **검증 부서를 따로 만들지 않는다.** 대신 일을 셋으로 나눈다.

| 일 | 누가 |
|---|---|
| **판정** — 설계를 읽고, 실제 코드·화면을 보고 맞는지 판단 | 에이전트 (MCP 로 설계를 읽고 코드베이스를 본다) |
| **기록** — 화면마다 상태 한 칸(`설계됨 / 구현됨 / 확인됨`) + 확인 시각·근거 | rockury (MCP 쓰기 도구로 받아 적는다) |
| **집계** — 능력별로 몇 개 중 몇 개가 어느 상태인지 | Features 화면 |

**MCP 는 읽기와 쓰기가 둘 다 필요하다.** 읽기만 열면 에이전트가 확인 결과를 되돌려줄 길이 없고, 판정이 대화창에서 휘발된다 — 그러면 "커버리지가 안 잡힌다"는 원래 문제가 그대로 돌아온다.

### 열린 도구

지목은 전부 **안정 주소**로 한다 — 저장소 id 는 무작위라 밖에서 알 수 없고, 주소는 사람도 에이전트도 읽고 쓸 수 있으며 이름이 바뀌어도 흔들리지 않는다.

| 도구 | 하는 일 |
|---|---|
| `list_ui_projects` | 프로젝트 목록 |
| `get_ui_tree` | 앱 › 서비스 › 화면 목차 + 상태 + 집계. **내용은 빼고** 준다(전체를 한 번에 읽지 않게) |
| `get_ui_surface` | 화면 한 장의 설계 내용 |
| `create_ui_node` | 노드 생성 — **부모 주소의 깊이가 층을 정한다** |
| `set_ui_surface` | 화면 내용 통째로 교체(읽어 고쳐 되보내는 왕복) |
| `set_ui_surface_status` | **확인 결과 기록** — 이 서비스의 핵심 |
| `list_ui_notes` | 사람이 화면에 남긴 **의견(요청)** — 화면별 전부 또는 프로젝트 전체의 미해결 |
| `resolve_ui_note` | 반영했다고 표시(지우지 않는다 — 이력이 남아야 한다) |
| `get_ui_tokens` | 프로젝트의 디자인 토큰 — **실제 코드의 토큰과 맞추라고** 있는 값 |
| `set_ui_tokens` | 토큰 덮어쓰기 — **준 값만** 바뀐다(통째로 교체하지 않는다) |

**의견은 사람 → 에이전트 방향**이라 만들기(`createNote`)를 열지 않는다 — 에이전트가 스스로 요청을 만들면 방향이 뒤집힌다. 반영 결과는 상태 칸의 근거로 적는다.

**열지 않는 것**: 이름·주소 고치기(`updateNode`)는 주소를 흔든다 — 흐름·규칙·의견이 전부 그 주소에 걸려 있어 에이전트가 무심코 바꾸면 가리키던 것들이 조용히 끊긴다. 삭제(`deleteNode`)는 연쇄라 되돌릴 수 없다. 둘 다 사람이 앱에서 뜻을 알고 한다.

**못 찾은 주소는 프로토콜 오류가 아니라 안내로 돌려준다** — "무엇이 왜 없는지 + 어떻게 확인하는지"를 담아야 에이전트가 스스로 고친다. 빈 결과를 조용히 주면 오타를 영영 못 찾는다.

## Surface: uiux.shell — 서비스 골격 (nav)

> 좌측 레일의 UI/UX 칸을 고르면 나타나는 뼈대. 화면 내용은 아직 없고 경로 배지만 보인다.

### Section uiux.shell.modules — 모듈·뷰 트리

- **AC-1** 좌측 레일에서 UI/UX 를 고르면 상단에 모듈 6개가 `Features · Screens · Flows · Rules · Style · Versions` **순서대로** 뜬다.
- **AC-2** 기본 진입은 **Features** 다(레일에서 서비스를 처음 고른 직후 보이는 화면).
- **AC-3** 뷰를 가진 모듈은 뷰 탭을 보인다 — Screens `Canvas · Spec · Review`, Style `Tokens · Components`, Versions `Timeline · Diff`. 나머지 모듈(Features·Flows·Rules)은 뷰 탭 없이 자기 자신이 화면이다.
- **AC-4** 모듈·뷰를 고르면 그 화면이 자기 경로 배지(예: `depth 3 · Screens › Spec`)를 보인다 — 지금 어디에 있는지가 화면만 보고 판별된다.
- **AC-5** 모든 leaf 는 셸의 순회 훅(`data-nav-service` / `data-nav-module` / `data-nav-view`)에 걸린다 — 화면 품질 게이트가 등록만으로 자동 순회한다(별도 등록 목록 없음).
- **AC-6** 모듈 id 와 같은 모듈 안의 뷰 id 는 서로 겹치지 않는다.

### Section uiux.shell.context — 컨텍스트 셀렉터

- **AC-1** 상단 컨텍스트 바에 `Project · Version · Viewport` 세 개가 뜬다.
- **AC-2** 세 셀렉터는 **모든 모듈에서 활성**이다 — 이 서비스는 구획(설계부/운영부)을 나누지 않으므로 모듈에 따라 꺼지는 셀렉터가 없다.
- **AC-3** Project 는 런타임 데이터라 아직 옵션이 없다 — 선택 안 된 상태로 시작하고 안내 문구(`프로젝트 선택`)를 보인다.
- **AC-4** Version 의 기본값은 `Draft`(편집 중)다.
- **AC-5** Viewport 의 기본값은 `PC` 이고 옵션은 `PC · 태블릿 · 모바일` 셋이다. 화면 계층이 아니라 렌즈이므로 모듈을 옮겨도 선택이 유지된다.

## Surface: uiux.screens.spec — 화면 구조 짓기

> 위계(앱 › 서비스 › 화면)를 만들고, 고른 화면의 구조(영역 › 요소)를 편집한다.
> Canvas 보다 이 뷰를 먼저 세우는 이유는 §6 에 있다 — 데이터가 서야 그릴 것이 생긴다.
> 3-pane: `[위계 | 구조 | 속성]`.

### Section uiux.screens.spec.hierarchy — 위계 트리

- **AC-1** 프로젝트가 안 골라졌으면 트리 대신 안내와 `새 프로젝트` 버튼을 보인다 — 설계는 프로젝트 안에 담기므로 그 전에는 만들 자리가 없다.
- **AC-2** 프로젝트를 만들면 **바로 그 프로젝트를 보게 된다**(컨텍스트 바가 자동으로 그것을 고른다). 만들자마자 빈 화면이면 무엇을 한 건지 알 수 없다.
- **AC-3** 앱·서비스·화면은 각각 부모 줄의 `+` 로 만든다. 만들기 폼은 네 층이 같다(이름 · 주소 조각 · 설명, 화면이면 종류 추가).
- **AC-4** 주소 조각이 규칙(§7 INV-2)에 어긋나면 **입력 중에 이유를 보이고** 만들기를 막는다.
- **AC-5** 같은 자리에 같은 주소 조각이 이미 있으면 저장소가 거절하고, 그 이유를 모달에 그대로 보인다(INV-1). 최종 판정자는 저장소다 — 화면이 먼저 그렸다가 되돌리면 "됐다가 취소된" 것을 보게 된다.
- **AC-6** 트리 줄의 지우기는 그 아래를 함께 지운다(INV-4). 무엇이 함께 사라지는지 버튼 설명에 적는다.
- **AC-7** 프로젝트는 트리에 없다 — 상단 컨텍스트 바가 고르는 축이라 트리에 또 두면 "지금 무엇을 보고 있나"가 두 곳에서 갈린다.

### Section uiux.screens.spec.structure — 화면 구조 (영역 › 요소)

- **AC-1** 화면이 안 골라졌으면 "왼쪽에서 화면을 고르라"고 안내한다.
- **AC-2** 영역(Section)을 추가하고, 영역 안에 요소(Component)를 추가한다. 요소는 **종류를 골라** 넣고, 종류 목록은 역할(입력·동작·표시·구성)로 묶어 보인다.
- **AC-3** 요소 id 는 종류에서 딴다(`input` → 두 번째는 `input-2`) — 흐름·규칙이 가리키는 손잡이라 사람이 읽을 수 있어야 하고, 무작위 값이면 눈으로 확인할 수 없다.
- **AC-4** 순서는 위·아래 버튼으로 바꾸고, 지우기는 그 조각만 지운다(영역을 지우면 안의 요소도 함께).
- **AC-5** 편집은 **먼저 화면에 반영하고 저장한다** — 트리 조작은 순수 함수가 이미 판정했고, 매 클릭마다 왕복을 기다리면 편집이 끊긴다. (위계 편집과 반대인 것은 판정자가 다르기 때문이다.)
- **AC-6** 화면을 떠났다 돌아와도 편집이 남는다.

### Section uiux.screens.spec.inspector — 속성

- **AC-1** 고른 것에 따라 화면 / 영역 / 요소 중 하나를 보인다. 고른 조각이 없으면 그 화면 자체를 보인다.
- **AC-2** 화면 속성은 **안정 주소**(`coupang.buyer.auth.login`)를 보인다 — 네 층의 주소 조각을 이은 것.
- **AC-3** 배치는 **방향(세로·가로·격자)과 칸 수**만 정한다. 좌표는 없다(§6) — 실제 픽셀은 뷰포트가 정하므로 화면 하나로 세 뷰포트가 성립한다.
- **AC-4** 상태(`설계됨`·`구현됨`·`확인됨`)는 보이기만 하고 여기서 고치지 않는다 — 판정은 설계를 읽고 실제 코드를 본 에이전트가 하고 앱은 받아 적는다(§8). 그 사실을 화면에 한 줄로 적는다.

## Surface: uiux.screens.canvas — 미리보기

> 고른 화면을 **실제 화면으로 보고 그 위에서 고친다**(§6 — "Canvas 는 별도 캔버스가 아니라
> 미리보기가 편집 가능해진 것"). 셸은 Spec 과 공유한다 — `[위계 | 미리보기 | 속성]`.

- **AC-1** 화면이 안 골라졌으면 "왼쪽에서 화면을 고르라"고 안내한다.
- **AC-2** 화면 구조(영역·요소·배치)가 기본 조각과 기본 토큰으로 그려진다. Spec 에서 고친 것이 그대로 반영된다(선택 상태를 공유한다).
- **AC-3** 폭은 **뷰포트 셀렉터가 정한다**(PC 1160 · 태블릿 768 · 모바일 390). 지금 어느 폭으로 보는지 헤더에 적는다 — 화면이 줄어 보일 때 "왜 작지?"가 아니라 "모바일이구나"로 읽혀야 한다.
- **AC-4** 자리가 좁으면 **통째로 줄여** 보인다(잘라내지 않는다). 잘라 보이면 "좁을 때 어떻게 되나"를 볼 수 없어 뷰포트를 두는 목적이 사라진다. 실제 크기(1배)보다 키우지는 않는다.
- **AC-5** 뷰를 바꿔도 위계와 속성은 그대로다 — 셸을 공유하므로 "같은 것을 다른 방식으로 본다"가 성립한다.

### Section uiux.screens.canvas.edit — 미리보기 위에서 고치기

- **AC-1** 요소를 누르면 그것이 골라지고 속성이 열린다. 빈 곳을 누르면 선택이 풀린다. 고른 요소는 외곽선으로 보인다.
- **AC-2** 요소를 끌면 **놓을 자리를 선으로** 보인다. 선은 앞뒤 요소 **사이**에 긋는다 — 요소 위에 겹쳐 그리면 "이 위에 얹는다"로 읽혀 뜻이 달라진다. 끌고 있는 요소는 흐려진다.
- **AC-3** 놓으면 순서가 바뀌고 저장된다. **저장되는 것은 좌표가 아니라 순서**다(§6). 다른 영역으로도 옮길 수 있다.
- **AC-4** 제자리에 놓으면 아무 일도 일어나지 않는다 — 집었다 놓기만 해도 저장이 도는 것을 막는다.
- **AC-5** 어느 영역에도 안 걸리는 곳에 놓으면 아무 일도 없다(빈 여백에 떨어뜨려도 엉뚱한 데 들어가지 않는다).
- **AC-6** 살짝 흔들린 것은 드래그가 아니라 **누르기**로 본다(4px 임계). 손 떨림이 의도치 않은 이동이 되지 않게.
- **AC-7** 끌어 옮긴 결과는 Spec 뷰의 순서와 같다 — 두 화면이 **같은 함수**를 부른다(`tree.ts`). 편집 규칙이 화면마다 갈리면 한쪽에서만 되는 조작이 생긴다.
- **AC-8** 미리보기 안에서는 글자가 잡혀 끌리거나 입력칸에 포커스가 가지 않는다 — 설계를 보는 곳이지 실제로 쓰는 곳이 아니다.

## Surface: uiux.features — 능력 인덱스

> 제품 한 줄 + 앱 › 서비스 › 화면 목차 + 완성 상태. **이 서비스의 첫 화면이자 목차**다.
> 사람은 여기서 훑고 파고들고, 에이전트는 같은 집계를 MCP 로 받아 "어디가 아직 안 덮였나"를 안다.

### Section uiux.features.header — 제품과 전체 상태

- **AC-1** 프로젝트 이름·주소 조각·설명을 보인다(제품 소개는 별도 모듈 없이 여기 헤더로 접는다 — §4).
- **AC-2** 완성도 막대는 **확인된 것만** 찬다. 구현만 된 것을 완성으로 세면 "다 됐다"가 거짓이 된다.
- **AC-3** 화면이 있는데 **확인이 하나도 없는 서비스**를 따로 짚는다 — 이게 "빠진 곳" 목록이다. 화면이 아직 없는 서비스는 넣지 않는다(설계를 시작도 안 한 것은 다른 이야기).

### Section uiux.features.index — 앱 › 서비스 › 화면

- **AC-1** 앱마다 카드, 그 안에 서비스 행, 펼치면 화면 목록. 각 층에 `화면 N · 확인 M` 을 보인다.
- **AC-2** **화면이 하나도 없는 앱·서비스도 빠뜨리지 않는다** — 만들어만 두고 아직 안 그린 자리가 목록에서 사라지면 "빠진 것"을 영영 못 본다.
- **AC-3** 화면을 누르면 그 화면을 고른 채 Screens › Spec 으로 건너뛴다 — 목차에서 본 것을 바로 고칠 수 있어야 목차 구실을 한다.
- **AC-4** 세는 단위는 **앱 › 서비스**다. 화면 단위로 세면("화면 42개 중 31개") 아무 그림도 안 그려진다.
- **AC-5** 모르는 상태 값은 `설계됨` 으로 본다 — 저장소가 열린 문자열이라 언제든 모르는 값이 올 수 있다.

### Section uiux.features.status — 상태 칸

- **AC-1** 상태(`설계됨` · `구현됨` · `확인됨`)는 **보이기만 하고 여기서 고치지 않는다.** 판정은 설계를 읽고 실제 코드를 본 에이전트가 하고 앱은 받아 적는다(§8) — 그래서 이 화면에는 상태를 바꾸는 손잡이가 없고, 그 사실을 화면에 한 줄로 적는다.
- **AC-2** 들어올 때마다 다시 읽는다 — 상태를 적는 주체가 화면 밖(에이전트)이라, 적었는데 안 보이면 "적힌 건가?" 가 된다.

## Surface: uiux.screens.review — 요소에 붙는 의견

> 화면 위 요소를 짚어 "이걸 이렇게 고쳐 주세요"를 남긴다. **스크린샷을 찍어 화살표를 그려 보내던
> 일을 대신하는 자리**다. 셸은 Spec·Canvas 와 공유하되 **오른쪽만 다르다** — 속성 대신 의견 목록
> (여기선 고르는 목적이 "무엇을 고칠까"이므로).

### Section uiux.screens.review.pin — 의견 남기기

- **AC-1** 의견은 **좌표가 아니라 요소에 붙는다.** 배치가 바뀌어도 떠내려가지 않고, 에이전트가 "어느 요소에 대한 말인지" 정확히 안다 — 이게 스크린샷과 결정적으로 다른 점이다.
- **AC-2** 요소를 누르면 그것이 골라지고, 어디에 남기는지 알려준다. 아무것도 안 고르면 **화면 전체**에 붙는다.
- **AC-3** 미리보기에는 **"의견이 있음"만** 점선으로 표시한다. 개수·내용은 옆 목록에서 본다 — 화면 위에 말풍선을 띄우면 정작 고쳐야 할 화면이 가려진다.
- **AC-4** 보내기는 손을 하나 더 얹어야 한다(`⌘/Ctrl + Enter` 또는 버튼) — 줄바꿈을 자유롭게 쓰면서 실수로 날아가지 않게.
- **AC-5** 빈 의견은 남길 수 없다.

### Section uiux.screens.review.list — 의견 목록

- **AC-1** 미해결이 먼저, 그 안에서는 오래된 것부터(대화 순서). 해결한 것은 접어 두고 개수만 보이며 펼칠 수 있다.
- **AC-2** 해결은 **지우기가 아니라 표시**다 — 무엇을 왜 고쳤는지가 이력으로 남아야 한다. 다시 열 수도 있다.
- **AC-3** 의견을 누르면 그 요소가 골라진다(목록 → 화면으로 건너뛰기).
- **AC-4** 가리키던 요소가 **지워졌으면 그렇게 표시한다** — 조용히 사라지면 무엇에 대한 말이었는지 영영 모른다. 의견 자체는 남는다.
- **AC-5** 화면을 지우면 그 화면의 의견도 함께 사라진다 — 가리킬 곳이 없어 유령이 된다.
- **AC-6** 에이전트가 MCP 로 읽는다는 사실을 화면에 한 줄로 적는다 — 남긴 것이 어디로 가는지 알아야 쓸 마음이 든다.

## Surface: uiux.style — 디자인 토큰

> 이 프로젝트의 색·간격·글자. 바꾸면 **미리보기가 즉시 그 얼굴을 갖는다** — 값만 보고는 그게
> 무슨 뜻인지 알 수 없으므로, 토큰 옆에 항상 그 결과를 함께 보인다.

### Section uiux.style.tokens — 토큰 편집

- **AC-1** **덮어쓴 값만 저장한다.** 기본 한 벌을 통째로 복사해 두면 나중에 기본이 좋아져도 이 프로젝트만 옛 값에 묶인다. 화면은 병합 결과를 보이고 저장은 차이만 남긴다.
- **AC-2** 빈 값은 **기본으로 되돌림**이다 — 지우기와 같은 뜻이라 따로 삭제 동작을 두지 않는다. 되돌리기 버튼은 덮어쓴 토큰에만 켜진다.
- **AC-3** 덮어쓴 토큰은 눈에 띄게 표시하고, 몇 개를 바꿨는지 알린다 — 기본에서 얼마나 멀어졌는지가 보여야 한다.
- **AC-4** 경로의 첫 조각으로 묶어 보인다(`color` · `space` · `font` …). 기본에 없는데 프로젝트가 더한 토큰도 함께 보인다(**열린 어휘** — 자기 토큰을 더할 수 있다).
- **AC-5** 이름은 **뜻으로** 짓는다(`color.primary`). `blue600` 같은 값 이름을 쓰면 나중에 색을 바꿀 때 이름이 거짓말을 한다.
- **AC-6** 오른쪽에 지금 토큰으로 그린 표본이 함께 뜬다 — 값을 고치는 즉시 반영된다.

### Section uiux.style.components — 컴포넌트 매트릭스

- **AC-1** 기본 조각을 역할(입력·동작·표시·구성)로 묶어 **지금 토큰으로** 그려 보인다. 토큰을 바꾼 결과를 한눈에 보는 자리다.
- **AC-2** 변형이 있는 종류만 여러 벌 그린다 — 없는 것을 억지로 늘리면 같은 그림이 반복될 뿐이다.
- **AC-3** 빈 컴포넌트는 무엇인지 알 수 없으니 **그럴듯한 표본 값**을 넣어 보인다.
- **AC-4** Style 화면도 미리보기와 **같은 격리**(그림자 뿌리)를 쓴다 — 앱 CSS 와 섞이면 여기서 본 모습과 실제 미리보기가 달라져 판단이 어긋난다.

### 아직 없는 것

- **앱별 덮어쓰기** — 지금은 프로젝트 단위다. 한 프로젝트 안에서 앱마다 다른 테마가 필요해지면 같은 병합 규칙을 한 겹 더 쌓는다.
- **조각(HTML) 편집** — 토큰은 고칠 수 있지만 조각 자체는 앱이 든 한 벌이 전부다.
- **3계층 토큰**(원시 → 의미 → 컴포넌트) — 지금은 평탄한 경로다. 경로 형태(`color.primary`)라 계층이 필요해지면 이름 규칙만 늘리면 된다.

## Surface: uiux.flows — 흐름 그래프

> "이 버튼을 누르면 어디로 가나"를 화면 사이 화살표로 본다. 이벤트는 **각 화면 안에 산다**
> (분산 선언) — 중앙 목록을 따로 두면 화면을 지웠을 때 그 목록만 낡는다. 여기서 하는 일은
> 그것을 모아 세우는 것뿐이다.

### Section uiux.flows.edit — 전이 붙이기 (Screens › 속성)

- **AC-1** 요소를 고르면 속성에 **"누르면"** 칸이 뜬다. 대상은 **같은 프로젝트의 화면 목록**에서 고른다 — 주소를 손으로 적으면 오타가 조용히 끊긴다.
- **AC-2** 종류는 이동 / 열기 / 닫기. 대상을 고른 뒤에만 보인다.
- **AC-3** **한 요소에 전이는 하나로 본다(v1).** 조건에 따라 갈리는 전이는 조건 어휘가 서고 나서 다룬다 — 지금 여러 개를 허용하면 편집 화면이 먼저 복잡해진다. 같은 요소에 다시 붙이면 갈아탄다.
- **AC-4** "아무 일도 안 함"을 고르면 전이가 사라지고, 그 화면에 남는 이벤트가 없으면 칸 자체를 지운다(빈 배열이 저장되면 diff 가 지저분해진다).

### Section uiux.flows.graph — 그래프

- **AC-1** 들어오는 전이가 없는 화면이 **첫 줄**, 거기서 몇 걸음인지로 줄이 갈린다. 순환이 있어도 멈춘다(전부 순환이면 첫 화면을 진입점으로 삼는다 — 아무것도 안 그리는 것보다 낫다).
- **AC-2** **가리키는 화면이 없어도 화살표를 지우지 않는다.** 오타나 지워진 화면을 조용히 감추면 "왜 안 이어지지?"를 영영 못 찾는다 — 끊긴 것으로 표시하고 위쪽에 모아 알린다.
- **AC-3** 데이터 변이는 **줄을 가르지 않는다**(화면 이동이 아니다). 자기 화면에 머무는 고리로 그린다.
- **AC-4** 화면을 누르면 그 화면이 골라진다(그래프 → 설계로 건너뛰기).
- **AC-5** 화면 내용이 깨져도 그래프 전체가 무너지지 않는다 — 읽을 수 있는 만큼만 그린다.
- **AC-6** 그래프 라이브러리를 쓰지 않고 **SVG 로 직접 그린다.** 배치는 순수 계산이고 그리기는 사각형과 선뿐이라, 의존성을 하나 늘리는 값보다 직접 만드는 값이 싸다(의존성 추가는 `main` 에서 한 명만 할 수 있는 일이기도 하다).
