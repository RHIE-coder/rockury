# Service: api-contract (판정 — Drift · Accept · Logs)

> **선언한 명세**와 **실제 서버**가 어긋났는지 본다. 이 서비스가 Swagger(선언만 봄)·
> Postman(실제만 봄)과 갈리는 자리다.
> 서비스 정본·도메인 모델·불변식은 `api-service.md`.

공통 불변식
- **판정 기준은 언제나 "이 프로젝트가 선언한 것" 하나뿐이다.** 업계 표준 준수를 판정하지
  않는다(`api-service.md` §4-②) — REST 는 팀마다 다르므로 그럴 근거가 없다.
- **판정은 두 등급이고 절대 섞이지 않는다**(§4-①). 관측 판정의 "이상 없음"을 완전 판정의
  "이상 없음"과 같이 보이면 앱이 거짓말을 하는 것이다.
- 판정은 **읽기만** 한다 — 서버를 고치지 않는다. 고칠 것은 리포트로 내보내 AI·사람이 한다.

## Surface: api-contract.drift (Drift 뷰)

### Section api-contract.drift.complete — 완전 판정
> 서버가 자기 스키마를 표준으로 뱉는 인터페이스에서만 성립한다. 스키마에서 서버를 만드는
> 방식이면 도로 뱉을 수 있고, 손으로 라우트를 짜면 뱉을 게 없다 — 그게 갈리는 이유다.

- **AC-1 (대상)** gRPC(server reflection) · GraphQL(introspection) · SOAP(WSDL) 만
  완전 판정 대상이다. 그 외 인터페이스에 완전 판정을 시도하지 않는다.
- **AC-2** 활성 환경의 서버에서 스키마를 통째로 읽어 선언한 명세와 전량 대조한다.
- **AC-3 (커버리지)** 결과에 **커버리지 100%** 를 명시한다 — 빠뜨린 게 없다는 사실이
  결과의 일부다.
- **AC-4** 서버가 reflection/introspection 을 꺼 두었으면 **완전 판정 불가**로 표시하고
  관측 판정으로 조용히 내려가지 않는다. 왜 불가인지를 갈래로 가른다:
  **기능 꺼짐 / 권한 없음 / 접속 실패 / 아직 안 만듦**.
  마지막 갈래(`not-implemented`)는 우리 쪽 사정이다 — 대상 인터페이스인데 아직 구현하지 않은
  경우(gRPC·SOAP)를 "서버가 안 준 것"처럼 보이게 하지 않으려고 따로 둔다.
- **AC-5 (1차 구현 순서)** GraphQL 을 먼저 구현해 판정 결과 화면·판정 로직을 세우고,
  같은 화면 위에 gRPC 를 얹는다. 결과 화면은 둘이 공유하므로 두 번 만들지 않는다.

### Section api-contract.drift.observed — 관측 판정
> REST · JSON-RPC · WebSocket · SSE · 웹훅. 서버가 자기 명세를 말해 주지 않으므로
> **실제로 쏴 본 것만** 안다.

- **AC-1** 실행 기록(Run)의 실제 응답을 선언한 응답 스키마와 대조한다.
- **AC-2 (핵심 — 커버리지 정직)** 결과에 **"N개 중 M개 관측 · K개 미관측"** 을 항상 표시한다.
  미관측 요청을 일치로 세지 않는다. 미관측이 0일 때만 "전부 관측됨"이라고 쓴다.
- **AC-3** 미관측 요청 목록을 따로 보인다 — 무엇을 아직 안 쏴 봤는지가 결과의 일부다.
- **AC-3b (판정 불가와 통과를 가른다)** 쏴 보긴 했는데 응답이 JSON 이 아니어서 **모양을 못 뽑은**
  요청은 관측으로 세지 않고 별도 목록(`unparsable`)으로 남긴다. "대조할 게 없었다"를
  "어긋남이 없었다"로 세면 안 된다.
- **AC-4** 같은 요청에 Run 이 여럿이면 **가장 최근 성공 Run** 을 기준으로 하되, 과거 Run 과
  응답 모양이 달랐으면 그 사실을 표시한다(서버가 도중에 바뀌었을 수 있다).
- **AC-5** 기준 버전이 다른 Run 은 섞지 않는다 — 어느 버전 기준의 관측인지 결과에 실린다.
- **AC-6 (스트림·수신 대조 — 맞출 선언을 못 정하면 통과가 아니다)**
  스트림·수신의 관측 내용은 응답 본문이 아니라 **메시지 목록**이다. 대조는 이렇게 한다:
  · **스트림 — 메시지의 이벤트 이름이 선언을 고른다.** `ResponseDef.status` 는 단발에선
    상태코드지만 스트림에선 "이벤트 종류"다. 선언에 없는 이벤트를 받으면 단발의
    "상태 X 를 받았는데 선언이 없다" 와 **같은 자리**로 잡는다(조용한 통과 아님).
  · **이름이 없는 메시지는 하나뿐인 선언에 갖다 붙이지 않는다.** 한 소켓에 여러 종류가
    흐르는 것이 WebSocket 의 보통 모습이라, 그 추측은 **조용히 틀린 판정**을 만든다.
    못 맞춘 것으로 세고 **건수를 결과에 싣는다**(0 이어도 싣는다).
  · **수신 — 선언은 응답 모양이 아니라 기대 본문**(`expectedBody`)이다. 받을 때 쓴 것과
    **같은 함수**로 다시 본다(규칙이 두 곳에 갈리면 한쪽만 고쳐진다).
  · **하나도 못 맞췄으면** 그 요청은 `unjudged` 다 — 관측은 있는데 어느 선언과 맞출지
    못 정했다는 뜻이고, 통과도 미관측도 아니다. 미관측은 *쏴 보면* 풀리고 이쪽은
    *이벤트 이름을 붙이거나 선언을 더해야* 풀린다.
  · **일부만 맞췄으면** 관측으로 세되 못 맞춘 건수가 남는다 — "전부 봤다" 로 읽히면 안 된다.
  · **가장 최근 세션 하나만** 본다(단발이 "가장 최근 성공 Run" 을 기준으로 삼는 것과 같은
    규칙 — AC-4). 지나간 세션까지 겹쳐 보면 이미 고친 어긋남이 계속 살아난다.
  · 스트림 Run 은 응답 본문 자리를 **비워 둔다** — 메시지 목록을 거기 밀어 넣으면 판정기가
    그걸 응답 모양으로 읽어 **없는 어긋남**을 만들어 낸다(불변식 ①의 반대 방향 위반).
  · **한 번도 못 붙은 세션은 관측이 아니다.** 접속 실패도 기록으로 남으므로 "행이 있나"로
    세면 안 된다.
  · **선언 모양이 아니라 그 실행이 무엇이었는지로 가른다.** 스트리밍으로 선언한 요청을 Send 로
    한 번 쏴 볼 수도 있고(막지 않는다), 그 단발 관측은 여전히 응답 본문 대조 대상이다.
  · **완전 판정도 같은 규칙을 쓴다** — 서버 스키마에는 스트리밍 루트가 아예 없어서
    (GraphQL introspection 에 subscription 이 없다) 규칙을 한쪽에만 두면 형제 경로가
    멀쩡한 서버의 subscription 을 "명세에만 있음"으로 잡는다.
  · **읽는 양을 묶는다** — 목록 조회는 메시지 본문을 안 싣고(그러면 앱이 멈춘다), 판정만
    요청마다 최신 세션 하나씩 따로 읽는다.
- **AC-7 (저장된 옛 판정 결과)** 판정 결과는 이력에 **JSON 통째로** 저장된다 — 커버리지에 칸을
  더하면 그 전 기록에는 없다. 읽는 자리에서 지금 모양으로 맞춰 준다. 안 맞추면 판정 화면이
  옛 기록 하나로 통째로 죽고, 재판정 버튼까지 사라져 스스로 복구할 수 없다.

### Section api-contract.drift.result — 판정 결과
- **AC-1 (결과 3종)** 항목마다 아래 셋 중 하나로 분류한다:

  | 결과 | 뜻 | 위험 |
  |---|---|---|
  | **서버에만 있음** | 내 명세가 뒤처짐 | 낮음 — 흡수하면 됨 |
  | **명세에만 있음** | 지웠거나 아직 안 만듦 | 높음 — 내 요청이 깨진다 |
  | **양쪽 있는데 다름** | 타입·nullable·필수 인자 변경 | 최고 |

- **AC-2** "다름"은 무엇이 어떻게 다른지 필드 단위로 보인다(선언 `string` ↔ 실제 `number`).
- **AC-3 (등급 표시)** 결과 화면 상단에 이 판정이 **완전**인지 **관측**인지 항상 보인다.
  한 Spec 안에 둘이 섞이지 않는다(인터페이스 종류가 Spec 고정 속성이므로 구조적으로 보장된다).
- **AC-4** 필수여부가 `모름`인 필드는 판정에서 제외하고, 제외한 개수를 결과에 표시한다.
- **AC-5** 어긋남이 0이어도 **커버리지와 함께** 보인다 — "이상 없음(7/12 관측)" 처럼.
  커버리지 없는 "이상 없음"은 표시하지 않는다.
- **AC-6** 결과를 사람이 읽을 수 있는 리포트로 내보낸다. 이 리포트가 **AI 가 코드를 고칠 때
  읽는 입력**이다(`api-mcp.md` § tools.read).

## Surface: api-contract.accept (Accept 뷰 — 명세로 흡수)

> 고칠 방향이 둘이다. **명세를 실제에 맞추는 것**은 Rockury 안에서 되고,
> **실제를 명세에 맞추는 것**은 코드 수정이라 Rockury 밖(AI·사람)의 일이다.

### Section api-contract.accept.absorb — 흡수
- **AC-1** "서버에만 있음"으로 나온 항목을 골라 Draft 명세에 반영한다.
- **AC-2** 흡수는 항상 **Draft 로** 들어간다. 버전 컷은 별도이고 사람이 한다.
- **AC-3** 흡수 전에 무엇이 추가·변경되는지 미리 보이고 사람이 수락한다. 자동 반영 없음.
- **AC-4 (불변식 ⑧)** 흡수 결과가 깨지는 변경을 만들면 승인 게이트가 뜬다
  (판정 규칙은 `api-studio.md` § versions.diff).

### Section api-contract.accept.report — 코드 쪽으로 넘길 것
- **AC-1** "명세에만 있음" · "다름" 항목은 흡수 대상이 아니다 — 코드가 틀렸을 수 있다.
  이것들은 **고칠 목록**으로 따로 모아 보인다.
- **AC-2** 그 목록을 리포트로 내보낸다. 항목마다 요청 이름 · 무엇이 어긋났나 · 어느 관측
  근거인지를 담는다 — AI 가 그대로 읽고 코드를 고칠 수 있는 형태여야 한다.
- **AC-3** Rockury 는 이 항목들을 **자동으로 명세에 반영하지 않는다.** 실제가 옳다고
  단정할 근거가 없다(서버가 버그일 수도 있다).

## Surface: api-contract.logs (Logs 뷰)

### Section api-contract.logs.history — 판정 이력
- **AC-1** 판정 실행마다 시각 · 환경 · 기준 버전 · 등급(완전/관측) · 커버리지 · 결과 요약을 남긴다.
- **AC-2** 흡수 이력을 함께 남긴다 — 언제 무엇을 명세로 받아들였나.
- **AC-3** 두 판정 이력을 비교해 "지난번엔 없던 어긋남"을 가릴 수 있다.
- **AC-4** 이력은 불변이다. 지나간 판정 결과를 고쳐 쓰지 않는다.
